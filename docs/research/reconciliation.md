# Cross-design rulings (controller), 2026-10-27

Settles contradictions the three builder checks found between the standard, plugin and prototype designs. These are builder's calls, not owner decisions; each design must adopt them and label them as such. Owner answers (pending) may override.

1. **Sensei model for a multi-path course.** One Sensei course per path (as on Learn). A plugin-owned "program" post type holds the course-level data (course IRI, placement AU and guide, teaching rules, badge declarations, custody option) and groups the path courses into ONE cmi5 course: program = `<course>`, each Sensei course = `<block>`, each lesson = `<au>`. The standard's one-package rule stands. "Course satisfied" maps to the program; block satisfied maps to Sensei course completion.
2. **Package contract.** The standard's ZIP (cmi5.xml + cxm/course.json + cxm/lessons/*.json) is the only interchange format, in two flavours (full; public with secrets stripped), versioned with an ETag. The plugin exports it from a program and imports it into Sensei (the prototype's P3 importer is in the plugin's scope), idempotently, via WP-CLI and REST.
3. **One writer per course.** For a course driven by a course server, only the course server writes learner statements to the LRS and mints the registration. The connector's direction 2 (Sensei on-site learning to xAPI) is a per-course setting, off for course-server-driven courses; its credential gets `statements/write` only for courses where direction 2 is on. Echo guard: the connector never re-emits statements for Sensei changes it applied from the LRS.
4. **Course import into the LRS.** The course server imports the package into the LRS (`courses/write`) on publish and on the content-changed ping; badge declarations come from course.json. The LRS needs the imported tree to recompute satisfaction before signing.
5. **Badge claim links.** The LRS mints a claim link per request, bound to actor + badge, single-use, 15-minute TTL, minting invalidates the previous one; scope `badges/claim-links`. The studio shows the claim page. The agent's `get_badges` returns badge metadata and a link to the course's claim page (which mints a fresh link after the learner is identified), never a bearer link. Normatively the standard defines only the `earned` statement and a claim-page URL; the issuer API is informative (our plugin's). Option 2 with a generic LRS that can't issue: the course server may sign as in option 3, declared in the course.
6. **Waived lessons and badges.** The standard's `countWaived` + `awardOn` (incl. `any-path`) are the rules; the plugin implements all of them. Lessons carried over from an earlier record version are waived with reason `Administrative` plus an extension `https://course-xapi-mcp.appsurd.org/extensions/carried-over`, and never count. A badge narrative states the tested-out count.
7. **Activity IRIs and Sensei completion.** Use the standard's scheme (activity id `{au@id}/au`, AU ids under the course's own IRI base). The prototype keeps its lesson slugs inside that scheme. The connector marks a Sensei lesson complete only when the AU's moveOn is met, computed from the imported course tree (not on cmi5 `completed`).
8. **Plugin as LMS side in custody option 1.** Out of the plugin's v1. The standard drops claims that "our WordPress plugin" acts as the option-1 LMS; keep it as future work.
9. **Course server ↔ connector routes.** In the plugin's scope: create anonymous WordPress user + actor, enrol, read progress (incl. tested-out), delete learner, status. Auth: Ed25519 signed requests (course server holds the private key; the plugin stores only the public key). Anonymous-user creation is rate-limited and capability-gated.
10. **Credentials.** Secrets never cross WP-CLI: the connector generates its own LRS secret and exposes only a hash for the LRS admin to register; no `wp config set` of secrets. Erase-actor is an API scope (`actors/erase`) callable by the course server and connector. "View my record" links are minted by the LRS through an API (`records/view-links`).
11. **Latency.** Target: a result appears in Sensei within 90 s p95; the 30 s figure is an aim, not binding. Both LRS delivery and connector inbox processing run at `shutdown` after responding, with cron as catch-up.
12. **Small contract values.** State document limit 2 MB. Block names use the plugin's namespace (`<plugin-slug>/beat`, `/checkpoint` with checks inside it, `/planted-bug`, `/rubric`), fixed before content migration; the name decision (owner question) sets the slug.
13. **Standard internals.** Review walk-throughs stay inside the current session (drop "launched with launchMode Review" from §8.1). After `maxAttempts` is spent and `failed` sent, a new session may retry and pass (cmi5 allows passed after failed); add a `restart_course` tool that starts a new registration. Identity in option 2: the course server is always its own MCP authorization server and federates login to the author's IdP (OIDC); the xAPI actor is `account {homePage: course IRI base, name: IdP subject}` unless the LMS/LRS assigns one.
14. **Agent auth in the prototype.** The prototype conforms: it implements MCP authorization in Functions (consent page reading the studio session; no extra login), not a bearer grant in tool arguments. Pending the owner's confirmation that this doesn't conflict with their "never touch OAuth/SSO configuration" rule.
15. **Status of builder's calls.** All BC calls in the three designs are provisional until the owner approves the documents.
